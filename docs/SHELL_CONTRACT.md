# SafeReturn — Shell Contract
**Decision (SEAN, 2026-10-20):** Desktop shell = **WinUI 3 (C#, Windows App SDK)** · Recovery shell = **native Win32 (Rust)** in WinPE.
This contract is how two UI codebases stay *one product*: same behavior, same words, same safety checks — only the rendering differs.

---

## 1. Architecture after the decision

```
┌─────────────────────────┐        named pipe (JSON, this doc)
│ WinUI 3 app (C#)        │ ───────────────────────────────► ┌──────────────────────┐
│ NOT elevated            │                                   │ safereturn-engine    │
│ Windows App SDK 2.5.1*  │ ◄─────────────────────────────── │ (Rust, elevated)     │
└─────────────────────────┘        progress / results         │ core + win + VSS     │
                                                              │ helper (S0)          │
┌─────────────────────────┐        in-process, same           └──────────────────────┘
│ Win32 PE shell (Rust)   │        message types (serde)
│ elevated by definition  │ ───────────────────────────────►  engine library
│ large-type, few screens │
└─────────────────────────┘
CLI (Rust) ── same message types, text rendering ───────────► engine library
```
\* Pin at scaffold: Windows App SDK **2.5.1 stable (2026-09-16)** per Microsoft Learn downloads (checked 2026-10-20; release-channels page lagged at 2.3.1 — downloads page + What's New agree on 2.5.1). Recheck before pinning; stable channel only, never Preview/Experimental.

## 2. The non-negotiables

1. **Shells render; the engine decides.** No backup/restore/safety logic in C# or in the PE shell. A flow's steps, order, defaults, confirmations, and error text all come from engine messages.
2. **Safety is enforced engine-side, twice.** The shell shows confirmations for humans; the engine *re-validates* every destructive request (SafeTarget checks: not the source disk, not the only-backup disk, size fits, session token matches the preview the user confirmed). A buggy or tampered shell cannot skip a check the engine owns.
3. **One wording source.** All user-visible strings live in a single strings table (id → text, with placeholders). C# and Rust shells both consume it; neither hardcodes copy. The Recovery Card and error messages are generated by the engine from the same table.
4. **Golden fixtures prevent drift.** The Rust `safereturn-contract` crate defines the message types; its test suite emits golden JSON files. The C# side has a matching test that deserializes every golden file. If a message shape changes, one side's tests go red before users see a mismatch. (Lesson imported from InstallScope PR #11: golden fixtures are where default/shape changes must show up.)
5. **The PE shell is a *subset*, by design.** Same flows, fewer screens: Restore, File Restore, Rehearsal results, Diagnostics. Settings/scheduling/history management are desktop-only. Where a screen exists in both, its contract messages are identical; the PE variant differs only in presentation (type size, density, input method).

## 3. Transport & protocol

- **Desktop:** named pipe `\\.\pipe\safereturn-engine-<user-sid>`, JSON Lines (one message per line, UTF-8), length-capped. Pipe ACL: current user only. Engine verifies the client process is the installed SafeReturn app (same install directory + signed binary once signing exists; until then, same-user ACL + a per-session token the engine issues to the app at launch via an inherited handle — spike item, flagged).
- **Versioning:** first message is `Hello { contract_version, shell, shell_version }`. Engine replies `Welcome` or `Incompatible { minimum_version }`. Mismatched shells show a plain "SafeReturn needs to be repaired/reinstalled" message — never a raw version error.
- **Framing rules:** requests carry `id`; responses echo it; engine→shell events (progress, log lines, prompts) are unsolicited but ordered. Long operations are *jobs*: `StartJob → JobEvent* → JobFinished`. Cancel is a request, not a pipe close.
- **In PE / CLI:** no pipe — the same serde types are used in-process (PE) or rendered as text/JSON (CLI `--json` uses the identical shapes).

## 4. Elevation model (desktop)

- The WinUI 3 app **never runs elevated** (store/MSIX norms, drag-and-drop, and basic hygiene).
- The engine is launched on demand with a UAC prompt when — and only when — a task needs it (backup, restore, media creation, rehearsal L3/L4). Browsing backups and file restore *to a folder* work without elevation where Windows permissions allow; the shell asks the engine `NeedsElevation { task }` rather than guessing.
- UAC copy is ours, shown *before* Windows' prompt: what needs admin rights and why, in one sentence.
- Scheduling: scheduled backups run via Task Scheduler under the engine directly (no UI). The app is a viewer/controller, never a requirement for a backup to happen.

## 5. Message catalog (v1 — implemented in `safereturn-contract`)

| Area | Messages |
|---|---|
| Session | `Hello`, `Welcome`, `Incompatible` |
| Discovery | `ListDisks` → `DiskList { disks: [DiskInfo] }` (model, serial suffix, size, is_system, is_backup_destination, volumes, warnings) |
| First Backup | `PlanBackup { destination_id, password_set: bool }` → `BackupPlan` (estimated size, space check verdict, plain-language summary lines, warnings) — password itself **never** crosses the pipe; the shell collects it and passes it once in `StartBackup`, engine holds it in protected memory only for the job |
| Jobs | `StartBackup`, `StartVerify` (rehearsal L1), `StartFileRehearsal` (L2) → `JobEvent { job_id, phase, done, total, unit, message_id }`, `JobFinished { job_id, outcome, summary }`, `CancelJob` |
| Restore | `ListBackups`, `BrowseBackup`, `PlanRestore` → engine-issued `RestorePlan { plan_token, target summary, erase_warning }`; `StartRestore { plan_token }` — the token binds the destructive action to the exact preview confirmed |
| Errors | Every failure is `EngineError { code, message_id, args, what_was_not_changed }` — shells render, never invent error text |

Types for the rows above marked v1-core are in the crate now; restore/media rows land with their slices (S4/S5) under the same rules.

## 6. What each shell must still do itself (presentation only)

- WinUI 3: NavigationView layout, Fluent styling, Mica, Store-grade accessibility verification (Accessibility Insights + Narrator pass per Learn checklist), MSIX packaging, window/DPI handling.
- Win32 PE: large-type theme, keyboard-first navigation, minimal screens, runs from RAM disk with no .NET/WinRT dependency.
- Both: implement the First Backup screen spec (S0 Findings §2) — tab order, accessible names, states — verified against the *same* checklist.

## 7. Open spike items (honest list)
- Session-token handoff from app → elevated engine without a race (named-pipe first-instance + token via inherited handle is the leading candidate; verify on Windows).
- Whether the engine should be an auto-start service instead of on-demand elevation (v1: on-demand; service adds install/attack-surface cost ordinary users don't need).
- C# contract test harness (golden-file consumption) — build with the WinUI 3 scaffold (S2-shell slice).
